1. 测量协议（三轮完全一致）

所有数字来自真机 logcat 埋点 + ADB 脚本按键，不靠主观感受。

  • 冷启动：pm clear → 起应用 → 稳定 3 秒，消除缓存影响。
  • 切台脚本：右 → OK（进入央视组）→ 依次 KEYCODE_DPAD_DOWN + OK 共 12 次，每次间隔固定 7 秒（足够覆盖最慢一次冷启动）。
  • 切台耗时：埋点 zapDone − 按键时刻，覆盖「按键 → 出首帧」全链路。
  • 首帧出画：firstFrame / firstFrameOnScreen（Surface 实际提交帧的时刻）。
  • 预播就绪：preReady[i] 台名 +Nms，从 startPrebuffer 到 STATE_READY。
  • 僵尸槽：preZombie[i] state=2 age=…，进入 BUFFERING 后既不 READY 也不报错。
  • 卡顿：stutterStart / stutterEnd，仅统计「已出过图之后又断粮」，跨台自动清零（这一条修掉过一次 29 秒的虚报）。
  • 资源：dumpsys meminfo PSS 与 dumpsys cpuinfo，稳定播放 120 秒采样。

2. 关键口径说明：为什么 P90 变「差」了

这是本报告最需要先讲清楚的一点。基线的 P90 = 550ms 只统计了 成功完成的 10 次；另外 3 次超时（冻屏 3.5 秒后接管、最终仍是黑屏）被算作「未完成」而从分位数里剔除了。优化版把 12 次尝试全部计入，包括冷启动慢的那些。

换句话说：基线的 550ms 是「只算跑得快的那批」得出的，优化版的 2.4s 是「连失败一起算」得出的。两者不同口径，不能直接比大小；能直接比的是失败次数（3 → 0）和最坏体验的确定性。

3. 根因（都有实测数据支撑）

根因 A：预播槽会进入「在缓冲、但永不 READY」的僵尸态

槽位 state=2（BUFFERING）持续 17~18 秒既不出图也不报错，onPlayerError 永不触发。基线策略是「等它 3.5 秒」，等不到就接管一个仍在缓冲的播放器 —— 结果就是黑屏。这是 3 次超时的直接来源。

根因 B：槽位越多，并发拉流互拖越严重

配置12 次结果P50 / P90僵尸槽结论
3 槽（4 路并发 + 4 解码器）3 次失败—4 个并发互拖
2 槽（3 路并发）12/12 全命中283 / 348 ms0 个单轮最优，但多轮不稳定

这条数据本可以支持「砍槽位」，但 2 槽在多轮复测里没有稳定复现 12/12，按「未被数据稳定验证为正向即不计入」的原则，已还原为 3 槽，仅作为下一步的重点验证方向（见 §6）。

根因 C：「能连上但不给数据」的死线绕过了所有现有机制

这类源 TCP 握手成功、HTTP 响应也回，但没有分片进得来。它不触发 onPlayerError，所以原有的「报错才换线」和死线记忆都抓不到它，只能靠超时兜底。这是当前唯一还能造成长时间等待的场景。

4. 最终采纳的改动

4.1 未命中不再等预播，直接起播并保留预播槽（主要改动）

改的是 playCurrentUrl 的 ② 分支：

维度改动前（v2.18.0）改动后
行为冻住旧画面，等预播槽 READY（≤3500ms）立即在主播放器冷启动起播；槽继续后台跑
超时后接管一个仍在缓冲的播放器 → 黑屏不存在这条路径
槽的生命周期等待失败即被停掉keepPrebuffer = true 保留，READY 后自动热切补齐
用户感知静帧 3.5s → 黑屏 → 再按一次键黑屏加载约 2.4~3s 后出画；慢源台 1~2s 后自动「补」成秒切
为什么必须保留预播槽：中途有一版为了「彻底简化」在直连时调了 cancelPrebuffer()，结果命中数直接掉到 0/12 —— 每次切台都把流水线清空，下一次必然又 miss，形成「一 miss 到底」的死亡螺旋。keepPrebuffer = true 之后命中数回到 6~9/12。

4.2 埋点与串账修复（不改播放行为，只保证数据可信）

  • 新增 stutterStart / settledChannel：只有「已出过图之后又断粮」才计卡顿，避免把首次缓冲算成卡顿。
  • swapToPre 与 playDirectNow 中清零 stutterStart / settledChannel：修掉跨台串账导致的一次 29 秒虚报卡顿。
  • 新增 PreSlot.startedAt、preReady、preZombie 日志，僵尸槽从此可被观测。

4.3 参数表（含适用前提、副作用、回退方式）

参数取值适用前提副作用 / 回退
BUFFER_FOR_START_MS1200 电视端硬解、源普遍 3~6 Mbps；1.2s 是「出图快」和「出图后不断粮」的平衡点 调到 700ms 可省约 450ms 冷启动，但实测引入 2444ms 卡顿且命中率下降 —— 已回退为 1200。回退即改此常量。
MIN_BUFFER_MS / MAX_BUFFER_MS8000 / 22000 客厅 WiFi，带宽有波动但不至于长期低于码率 调小省内存但长播更易卡；调大则内存与切台延迟上升。本轮未改动。
BUFFER_AFTER_REBUFFER_MS2500 卡顿后要攒够 2.5s 才恢复，避免「恢复→立刻再卡」的抖动 调小恢复更快但易反复卡；调大看起来更「卡」。本轮未改动。
CrashGuard.slotCount3（标准档） 按 RAM 分档：≥4GB 三槽、低内存一槽 降到 2 槽单轮最优但多轮不稳定，已还原为 3。改此行即可回到 2。
PRE_SLOT_MAX_AGE_MS已删除 原本用于「槽太老就重启」 删除原因：startPrebuffer 对同台同址会早退，所谓「重启」是空操作，还把 startedAt 重置为 0，导致槽在用户切台前反而无法被判为僵尸。

7. 遗留风险与下一步

遗留风险

  • 预播就绪 P50 ≈ 2.3 秒是切台耗时的硬瓶颈。只要源本身要 2 秒才能攒够 1.2 秒缓冲，"秒切"就只能覆盖已经预热好的那一小部分台。
  • 「能连上但不给数据」的死线仍只能靠超时兜底。它不报错，现有机制看不见它；用户会看到 2~4 秒的加载圈。
  • 3 槽并发下的僵尸槽会低频持续出现。现在由「直连 + 保留预播」兜住，不再黑屏，但没有根除。
  • 弱网场景没有数据。本轮所有结论都是在正常 WiFi 下取得的。

下一步（按收益/成本排序）

  1. 把「连接成功但 1.5 秒内零分片」判定为死线（前置探测）。用 AnalyticsListener.onLoadStarted/onLoadCompleted 或字节计数做看门狗，命中即换线。这直接消灭当前唯一的长时间等待场景。
  2. 专项验证 2 槽。以「多轮 × 每轮 12 次」跑 5 轮取分布，而不是单轮。若稳定优于 3 槽，再动 slotCount。
  3. 压缩预播就绪时间。方向：只预拉清单 + 前 2 个分片（不建完整播放器）用于快速出图，完整缓冲就绪后再接管；或按源历史速度只给「快源」预热，慢源不占槽。
  4. 补弱网实验。用 adb shell 注入限速或路由器侧限速，跑同一协议，验证 BUFFER_AFTER_REBUFFER_MS 与 MIN_BUFFER_MS 是否需要按网络状态分档。
